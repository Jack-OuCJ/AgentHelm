# AgentHelm App 模式设计

2026-10-22。需求边界已确认；本文给出实现方案，不代表功能已交付。尚未修改运行配置、启动会话或调用模型。

## 已确认的使用方式

用户在 CCD 或 Codex App 中指定一个已有会话作为 Dispatcher。Dispatcher 收到任务后，创建目标 App 内可见的独立 Lead 会话，传入任务上下文，并跟踪进展与结果。用户可以打开 Lead 会话查看过程、补充要求或接手。

首期只做同 App 调度：CCD Dispatcher 调度 CCD Lead，Codex App Dispatcher 调度 Codex App Lead。跨 App 调度不属于首期。

Lead 承担单个任务的设计、执行协调、验收与结论；Executor 优先使用 Lead 的原生子代理。Lead 和各 Executor 角色均可以单独指定模型与推理强度。

## 当前实现与缺口

以下事实来自本工作区源码读取：

- `bin/spawn-lead` 在 `cli-herdr` 分支创建 Herdr tab 并启动 CLI；其他分支只打印启动提示。
- `bin/run-executor` 按角色模型表启动 CLI，并不会因为运行环境是 App 就改用 App 原生子代理。
- `.agenthelm/config/env` 是工作区级配置；现有 `bootstrap` 据此选择所有会话的环境说明。
- `.agenthelm/config/role` 是工作区级角色标记，尚不能代表用户指定的唯一 Dispatcher 会话。
- `bin/new-task` 在调用 `spawn-lead` 前就写入 `running`，因此任务状态不能用于证明 Lead 已实际启动。
- 当前未找到用于 App 调度的任务与会话 ID 绑定记录。
- Herdr 提供 `list/get/read/wait/prompt`；`wait` 可等待 `idle/working/blocked/done/unknown`。本项目的 `lead-watch-start` 是上下文恢复钩子，不是常驻 watcher。

外部能力证据应与项目实现分开：

- 当前 Codex App 对本会话开放了创建独立聊天、续发任务、等待结果及模型参数；项目尚未接入，也未验证 AH 的完整链路。
- 用户提供的 CCD 调查报告列出了已有会话的读取、发消息和切模型工具，但报告中的 `start_session` 未开放。该报告不能证明当前 CCD 已具备自动新建 Lead 的能力。
- Codex 的独立 `app-server` 提供线程控制协议，但其存在不能证明由另一个服务创建的会话会出现在当前桌面 App 中。不能以此替代 App 内可见性验收。

## 运行入口与会话绑定

保持角色定义共用，分别识别 `cli.claude`、`cli.codex`、`app.ccd`、`app.codex` 四种运行入口。

`.agenthelm/config/env` 保留为新会话的工作区默认值，兼容现有 CLI 使用方式。已有会话以自己的绑定为准；将某个 App 会话注册为 Dispatcher，不改写其他会话的运行语义。App 创建的 Lead 继承本次调度的运行入口，不重新读取工作区默认值后切回 CLI。

调度关系记录在本工作区 `.agenthelm/state/` 中，包括：工作区、运行入口、唯一 Dispatcher 的会话标识，以及任务对应的 Lead 会话标识。绑定记录可包含实际模型、推理强度和最后观测状态，但不存放凭据。

运行入口信息必须贯穿创建、委派、恢复和状态读取。仅在启动提示中声明角色，不等于完成会话注册或取得调度职责。

创建 App 会话时关联当前工作区，并显式传入角色与任务绝对路径。任务操作以任务目录为工作目录；不得把提示词中的目录声明当成底层进程已切换目录的证明。

## 模型配置方案

继续使用 `.agenthelm/config/roles.toml`，保留现有角色、CLI `candidates` 和 CLI 命令模板。新增按 App 区分的默认值与角色覆盖，不复制整份角色表，也不直接修改生成的 `models.md`。

下面是拟新增的格式示例，尚未写入真实配置；示例模型不代表替用户作出实际分配：

```toml
[app.defaults.ccd]
model = "default"
effort = "default"

[app.defaults.codex]
model = "default"
effort = "default"

[roles.lead.app.codex]
model = "gpt-6.1-sol"
effort = "high"

[roles.hard.app.codex]
model = "gpt-6.1-sol"
effort = "xhigh"

[roles.fact.app.ccd]
model = "default"
effort = "default"
```

解析按字段采用以下顺序：当前角色的目标 App 配置，目标 App 的公共默认配置，目标 App 原生默认值。

- App 的 `model = "default"` 表示目标 App 为新会话采用的默认模型，不表示 Dispatcher 当前模型，不使用 CLI 候选解析。
- App 的 `effort = "default"` 表示所选模型在目标 App 下的默认推理强度，不隐式继承 Dispatcher 的临时选择。
- CLI 的 `claude:default`、`codex:default` 继续只表示对应 CLI 的默认配置。
- 给已有 Lead 续发任务时保留它的实际模型和推理强度，不因追加消息重新套用新会话默认值。用户明确要求调整时再验证并应用。
- 原生子代理可能默认继承父会话。适配必须验证并设置解析后的模型与强度，不能把继承行为误当成目标 App 默认。无法解析或设置时应报告能力缺口。
- 显式模型、推理强度或其组合不可用时，报告具体错误，不静默换模型、降强度或改走 CLI。
- Dispatcher 当前模型由用户控制，注册角色不自动修改它。

生成模型表时分别展示 CLI 命令与 App 模型绑定，标明实际入口。App 配置不生成一个伪装成原生会话的 CLI 命令。

## App 接入方式

App 模式需要项目侧的请求校验与绑定管理，也需要运行在宿主内的智能体调用真实会话工具。普通 Python 脚本不能直接调用仅在聊天中暴露的原生工具。

项目侧负责解析角色和模型配置、产出完整委派信息、保存任务与会话 ID、校验调度归属。宿主侧负责创建会话、发送首轮任务、设置模型与推理强度、读取结果和等待会话。

接入前逐项确认宿主能力：创建可见独立会话、发送首轮任务、读取及等待状态、追加任务、配置模型和强度。会话 ID、目录、首轮执行和有效模型必须有实际证据，不能仅以工具调用被接受作为成功。

CCD 自动创建能力尚未验证，属于当前已知接入缺口。若当前宿主未开放该能力，应清楚阻止此次自动创建；深链接预填、手动发送和后台 CLI 均不能作为满足需求的验收结果。不得修改全局配置、安装插件或绕过服务端开关来掩盖缺口。

## 分派与跟踪

每个任务保存一个当前 Lead 的会话标识。创建失败时不能将任务描述为 Lead 已在执行；任务目录、启动尝试和实际运行需要区分。

跟踪对齐 Herdr 的识别、读取、等待和追加任务能力。会话空闲、结束或输出了内容，不自动代表任务验收通过。任务进展继续由 Lead 使用 `bin/status` 写入本地 `STATUS`，Dispatcher 结合会话事件和任务证据汇总结果。

Dispatcher 可以在运行中等待原生事件并处理完成、失败和需要用户输入的情况；本设计不新增常驻 watcher、cron 或全局定时任务。主控未运行时不宣称持续监控，恢复时从绑定记录和任务状态重建视图。

沿用已有并发配置，并遵守目标 App 的实际限制；不因 App 模式绕开大型构建、测试与浏览器串行要求。

## 主控交接与人工介入

同一工作区同时只有一个有效 Dispatcher。用户指定新主控时，先确认原主控交接，再转移调度归属并载入已有任务及 Lead。无法确认交接时报告冲突，不自动抢占，也不停止其他会话。

原主控交接后不再分派任务。绑定检查必须发生在分派操作之前，避免仅更新记录而旧主控仍继续创建 Lead。

用户可以直接在 Lead 会话中补充或调整任务。Dispatcher 读取 Lead 最新状态及指令后再行动，不自动重发旧任务，不覆盖人工调整；新要求不扩大已有权限或代替必要的用户授权。

恢复时先复用已有 Lead，核实它是否仍存在及其当前状态。无法确认会话状态时标明未知，不直接重建并触发重复执行。

任务完成后保留 Lead 聊天并移出活跃跟踪列表，不自动删除或归档。Herdr 关闭 tab 的规则不套用到 App 历史会话。

## 验收标准

1. 用户指定的已有会话成为唯一 Dispatcher，不修改该会话模型，也不将其他根目录会话自动视为主控。
2. 一次分派创建一个目标 App 内可见、可打开的独立 Lead；正确关联任务，并实际执行首轮任务。
3. CLI 与 App 同时使用同一工作区时，模型解析和会话恢复互不串用运行入口。
4. Lead 与各 Executor 角色的模型及推理强度按配置生效；默认值与显式值都能读取或验证实际结果。
5. 指定模型不可用、创建能力缺失或启动失败时，错误明确，不误报运行，不静默回退。
6. Dispatcher 能读取多个 Lead 的状态、等待变化、追加任务，并区分会话空闲与任务完成。
7. 主控交接及恢复复用已有 Lead；旧主控失去分派资格，冲突不会导致重复创建。
8. 人工调整后，Dispatcher 不重放旧要求；完成任务的聊天保留且不再处于活跃跟踪。
9. 配置解析和生命周期逻辑用替身验证；真实 App 会话链路另行验收。替身通过不算 CCD 或 Codex App 已接通。

## 实现顺序

先验证两端关键原生能力，再实现会话入口与调度绑定、兼容的模型解析、创建和跟踪、交接恢复，最后分别验收 CCD 与 Codex App。各端独立报告通过项和缺口，不以某一端可用推断另一端可用。
