02定位方法 · 案例 A（runtime）

案例 A：卡死一整天，“自愈”其实是发布杀掉了僵尸进程

经验：三种时钟先对齐
  • message 表UTC
  • thinking logUTC-7
  • CLSUTC 毫秒
证实表象或否证越往右上越接近根因
症状
多个 chat 卡死一整天
次日用户称“自己好了”。工单账号与 chat 归属不同，先锁定真正卡死的 chat。
假设 1 · 表象
主循环僵死
DB 心跳冻结；用户消息照常入队，但无人回复。
假设 2 · 证实
判活出错
CLS：心跳 stale + lockfile fresh 持续约 6.5h，被判为活，拒绝 respawn。
假设 3 · 证实
子进程半死
Thinking Log：stop 已请求，keep_alive 仍每 10s 刷新 lockfile。
“自愈” · 否证
滚动发布杀掉僵尸进程
新 deployment 首条日志与恢复时间重合；用户上线后判 lockfile_stale，自动 respawn。
根因
两层叠加的平台 bug
子进程半死 + 判活漏判：birth_age=None 让僵尸兜底失效。
验证
新版兜底 180s 内恢复
同类场景由新的僵尸锁检测自动处理；遗留两项另行跟进。
02定位方法 · 案例 B（billing）

案例 B：账本精确对账，否掉两个假设，结论是真实消耗

对账原则

唯一真源：user_credit_accounts

先把两套 user_id 映射对齐，再逐周期对账。

证实否证
症状
迁移后 credits 归零
用户称归零两周、年付未到账。完整对话未读，缺口写明在案。
假设 1 · 否证
年付未到账
有一笔 complete 支付，同一秒充入月额度，订阅有效；早先 expired 订单是未付尝试。
假设 2 · 否证
迁移丢失或空扣
终身用量 = 各周期之和，精确对上；没有空扣，也没有重复扣。
假设 3 · 证实
真实消耗
约 48h 内由真实模型调用耗尽；耗尽时间与用户感知吻合。
结论 · 已确认
无平台 bug
Langfuse 缺凭据，该项单独列为待确认。
产品建议
耗尽时提示重置日
回复告知重置日与补充选项；工单按非缺陷关闭。

03Skills 写法

范例 helpflow-cls-logs：102 行分七节，每节管一个决策

SKILL.md
  • 3–8description适用范围、能力、触发动作、与 Kibana 的优先级：一段同时管召回和路由
  • 13–27核心配置固定用镜像预装的 tccli，列出禁止的 fallback；凭据只写变量名
  • 29–46只读契约6 条白名单命令；SearchLog 的必填参数、Limit 上限与大小写
  • 48–58使用时机先查 CLS 的五类场景；Kibana 查不到不代表请求不存在
  • 60–68查询流程时间窗 → 元数据 → 最窄查询 → 上下文 → 判失败 → no-hit 修正一次 → 脱敏回复
  • 70–94命令示例两个可直接套用的命令形状，参数全部占位或取自环境变量
  • 96–102排错按“现象 → 允许的动作”写，每条同时写明禁止的动作
03Skills 写法

八条写法值得照抄，四个反模式要避开

01
description 写触发词，也写不触发

引号列出触发短语，再补“不触发：代码开发…”

02
只读白名单契约

逐条列允许的命令、必填参数与上限

03
no-hit 停止条件

空结果记为 no-hit，最多修正一次就换源

04
写前预览，确认后执行

展示目标与精确改动，批量操作逐条确认

05
references 渐进披露

SKILL.md 只放流程，表结构放到 references

06
把踩过的坑写进正文

列名陷阱、两套 ID 映射、接口兼容绕行

07
先识别输入，缺了就问

先提取 chat ID 与环境，缺必需输入直接问

08
Red Flags 与 Checklist 收尾

结尾自检，防止漏步

反模式
  • ×双目录手工复制

    4 个同名 skill 内容已不一致

  • ×硬编码易变值

    日志主题 ID、内网地址直接写进正文

  • ×长 SKILL.md 未拆分

    379 行、373 行的 skill 没有 references

  • ×跨 skill 口径冲突

    source 名、数据库回退规则各说各话

  • 02每个数据源写明 no-hit 停止规则
  • 03证据分级：已确认 / 强推断 / 待确认
