# Research details (read when the situation arises; main rules are in AGENTS.md)

## Strict mode (when the user calls a task important)

On top of the defaults:
- At least 3 seeds; report mean ± standard deviation and keep failed runs.
- Record the SHA-256 (Linux `sha256sum`, macOS `shasum -a 256`) of the evaluation scripts and gold data before running and verify them at the end.
- Hold out one data split that is never looked at during iteration; run it once, at the end.
- Run one negative control (disabling the core component should make results worse).
- Afterwards, an independent read-only delegate gets only the logs and code and recomputes a subset of the numbers. Keep per-sample predictions or outputs for this, not only aggregate metrics.

## Long runs (remote, or several hours)

- Before scaling up, each system under test runs the first item end to end in the target environment (remote means remote) and its artifacts are inspected. A local dry run does not count.
- The driver writes `failures.jsonl` per item (item ID, stage, exit code, log path). When one system fails 3 items in a row, stop that system and run `bin/status blocked "<why>"`; never let it finish silently. Support resuming from where it stopped.
- Write the reasons for fixes and reruns into the README (or a `FRICTION.md` next to it); the process record matters as much as the design.
- Remote execution is environment-specific. Wrap it in your own start/status/clean script and name it in `local.md`; it should leave a local marker when the run ends so a later session can check without a resident watcher.

## Lead context handover

- After each milestone, update STATUS. Anything to remember long term (user decisions, pitfalls hit, conventions) goes into the task's `memory/`: one note per file plus a `memory/MEMORY.md` index of one line per note. Do not write separate handover files.
- After `/clear` or compaction, `bin/lead-reload` (run by the session-start hook at the task root) injects STATUS, this task's conclusion lines from `INDEX.md` and `memory/MEMORY.md`. After 3 compactions it reminds the Lead: once the next milestone is done, tell the dispatcher the session can be cleared. The user clears when idle.

## Cleanup and conflicts (mostly done while writing; the periodic pass every two weeks)

- Closing a task: delete virtual environments, downloaded data and models, regenerable intermediates, caches and remote scratch. Keep README, specs, task files, `results.jsonl`, check output, `FRICTION.md` and per-sample predictions or outputs (needed for rechecks). `bin/kb lint` warns about large finished task directories.
- Indexes: `INDEX.md` and `EXPERIMENTS.md` are generated by `bin/kb index`; never edit them. Fix what `bin/kb lint` reports (missing fields, duplicates, missing supersede targets, scripts named in rules that no longer exist, size budgets, cleanup) as you go. A replaced card gets `superseded_by`; a task conclusion that is withdrawn, overturned or needs recheck is marked in the conclusion text as below.
- Periodic pass (dispatcher, every two weeks, no scheduled job needed): run `bin/kb lint`; move stray memory notes to the task or project they belong to; have a cheap role read the rules and memory and list contradictions for the user; commit the private rules.
- Expiry: conclusion lines carry a date and model/tool versions. Treat model and tool tests older than 60 days as stale when reading; no upkeep needed.
- Confirmation and conflict: when a new conclusion answers the same question as an old one:
  - Same answer: append `confirmed by <id>` to the old Tendency line.
  - Opposite answer: the Lead and one independent reviewer (review role, given only the two READMEs, specs and results) each judge separately. Criteria: strict mode beats quick; more samples beat fewer; held-out beats none; newer tool versions beat older for tool tests. If both verdicts agree, append `overturned by <id>` to the loser's Tendency line. If they disagree, append `conflict: <id> <one line>` to both and hand it to the user.
  - Write both judges' reasoning to the new task's `findings/conflict-<old-id>.md`.
  - Before editing the README, find the cause: if one side is wrong (evaluation bug, too few samples, old version), mark it withdrawn or overturned; if both hold under different conditions, write the conditions into the conclusions so they no longer contradict.
- Withdrawal: when an evaluation bug is found, mark the conclusion `withdrawn: <reason>` and mark conclusions that depend on it `needs recheck`.
- Board mirror: the local README is the source of truth. If a Notion board is configured, rerun `bin/status done …` after editing a conclusion so the mirrored conclusion is refreshed.
