# App 模式规格

状态：ready-for-agent。来源：已接受的 App 模式设计与 ADR 0001。用户已授权直接编写规格、拆分任务、实现与审查，无需中间确认。

## Problem Statement

用户希望在 CCD 或 Codex Desktop 指定一个已有聊天作为 Dispatcher，在同一个 App 中自动创建可见、可继续交互的独立 Lead，并按角色选用模型与推理强度。当前工作区只会在 Herdr 中自动启动 CLI，App 路径只打印提示，不能证明 Lead 已创建或运行，也没有唯一主控与恢复绑定。

## Solution

保留共享角色、任务目录与 STATUS，新增由项目 CLI 与宿主原生工具共同执行的 App 协议。项目负责绑定、权限归属、请求与回执验证；宿主智能体负责真正调用 App 工具。每次原生操作都先取得完整请求，完成后提交与请求关联的证据。缺少能力时明确失败，不回退到 CLI，不把排队或生成提示视为执行成功。

## User Stories

1. 作为用户，我希望指定已有会话为唯一 Dispatcher，以便从熟悉的聊天开始工作。
2. 作为用户，我希望注册主控不改动其模型，以便保留我的当前选择。
3. 作为 Dispatcher，我希望创建同 App 的独立 Lead，以便用户可以查看和接手。
4. 作为 Lead，我希望收到工作区、任务目录、角色、可写范围和验收要求，以便正确执行。
5. 作为用户，我希望 CLI 与 App 会话并存，以便不用修改整个工作区的运行默认值。
6. 作为用户，我希望每个角色独立选择 App 模型和推理强度，以便匹配任务复杂度。
7. 作为用户，我希望未指定值使用目标 App 默认，以便不会误用 Dispatcher 的临时选择。
8. 作为用户，我希望显式参数不可用时报错，以便不会静默降级。
9. 作为 Dispatcher，我希望失败或排队中的创建不会标为运行，以便任务进度可信。
10. 作为 Dispatcher，我希望重复创建被拦截，以便不会让两个 Lead 重复执行同一任务。
11. 作为 Dispatcher，我希望列出、读取和等待 Lead，以便掌握进度及输入请求。
12. 作为 Dispatcher，我希望追加任务时保留 Lead 的实际模型，以便不会意外重新配置。
13. 作为用户，我希望空闲和任务验收完成分开，以便不会误报交付。
14. 作为用户，我希望人工修改后的最新上下文优先，以便调度者不会重放旧任务。
15. 作为用户，我希望主控交接保留已有 Lead，以便连续推进任务。
16. 作为用户，我希望旧主控失去分派权限，以便避免并发抢占。
17. 作为 Dispatcher，我希望恢复时保留未知状态，以便不会把无法查询误当作会话不存在。
18. 作为用户，我希望完成后保留聊天并停止活跃跟踪，以便查看历史。
19. 作为 Lead，我希望 Executor 使用原生子代理且验证实际模型，以便不会退回后台 CLI。
20. 作为用户，我希望能力缺失的 CCD 明确阻止自动创建，以便交付声明真实。
21. 作为维护者，我希望协议可以离线验证并保留现有 CLI 行为，以便安全迭代。

## Implementation Decisions

- 运行入口区分 cli.claude、cli.codex、app.ccd、app.codex。工作区默认配置只用于无绑定会话；显式会话绑定与恢复信息优先。
- App 状态使用工作区本地 JSON、原子写与进程锁，保存唯一 Dispatcher、归属版本、Lead 绑定、能力证据和操作请求。拒绝工作区外路径与符号链接逃逸。
- 使用 prepare/result 两阶段宿主协议。请求包含唯一标识、操作类型、会话归属版本、任务绝对目录、目标运行入口和委派上下文。宿主只执行请求声明的操作，不能以 CLI 替代原生工具。
- 分派在准备及回执时验证唯一主控。待确认的外部创建保留占位，未知结果阻止重复创建；交接遇到未决写操作应报冲突，避免旧请求在新主控接手后执行。
- 回执验证目标 App、工作区关联、会话标识、可见性、任务目录、首轮实际执行和有效模型/强度；缺失证据不进入运行状态。排队标识不是最终会话标识。
- 目标 App 能力逐项声明并保留来源；缺少创建、读取、等待、追加或模型验证能力时报具体错误。CCD 不预置为支持自动创建。
- 角色 App 配置按字段采用角色覆盖、App 公共默认、App 原生默认。default 不解析 CLI 候选，不隐式继承父会话。已有 Lead 的追加消息保留实际设置。
- CLI 模型选择与现有命令模板保持兼容；生成模型表同时展示 App 绑定，不伪造 CLI 命令。
- 读取与等待作为宿主请求，返回会话观察；任务是否验收完成仍以 STATUS 和验收证据判断。未知会话不自动重建。
- 追加任务前读取最新上下文；请求与最近一次观察关联，人工介入后需重新观察。恢复只生成读取请求，不重发旧任务。
- 主控交接必须由原主控明确释放并指向新会话，新主控才能接管；保留 Lead 绑定及实际配置。同 App 交接，跨 App 不在范围内。
- 任务完成时从活跃跟踪移出，保留聊天。无常驻 watcher、cron、全局配置、账号或权限修改。
- 普通脚本无法直接调用聊天内工具；交付包含宿主执行规则与可验证请求，不能宣称 Python 自身已调用原生 App。

## Testing Decisions

- 用户已授权跳过中间确认；本规格固定测试接缝为公开 CLI 的 JSON 请求/回执与现有角色启动命令。
- 使用现有 unittest 临时工作区、隔离 HOME、替身 CLI 模式。只在宿主工具、外部进程等系统边界替身，不 mock 内部方法。
- 每个纵向切片先增加一个公开行为失败用例，再实现。验收默认解析、显式错误、路径边界、唯一主控、重复创建、并发、回执缺失、交接、恢复、人工介入和历史保留。
- 现有 Herdr、plain CLI、安装、规则恢复、可迁移性和全局配置不变契约需回归。
- 原生能力核查与端到端执行分别记录。真实链路未执行、宿主不开放能力、有效参数无法读取时，明确标记未验证或能力缺口；离线替身通过不能关闭真实宿主验收。

## Out of Scope

跨 App 分派、独立 app-server 冒充 Desktop 可见会话、后台 CLI 回退、自动归档、常驻监控、全局安装与配置、绕过宿主权限、自动推送及外部消息。
